# Solution Overview: Grid Guard

## What Grid Guard Does

Grid Guard is a decision-support system for utility grid operators. It continuously
ingests asset sensor telemetry, multi-day weather forecasts, and historical outage
incident records, fuses them into a unified feature representation, and produces two
outputs:

1. **A ranked risk list** — every monitored asset scored by failure probability and
   weighted by the consequences of that failure for the grid and its customers.
2. **A plain-English maintenance and crew dispatch plan** — generated by IBM Bob
   (powered by watsonx.ai) directly from the ranked risk list, ready for field teams
   to act on without further interpretation.

The system is designed so that an operator arriving for a shift can open the
dashboard, see which assets are at greatest risk today, understand *why* each is
flagged, and hand a concrete action plan to field crews — all without writing a
query, running a script, or manually correlating data across systems.

## Core Mechanism

### Step 1 — Multi-Source Data Fusion

Raw data from three independent sources is normalised and loaded into a shared
Neon Postgres database:

- **Asset sensor telemetry** (temperature, vibration, partial discharge, oil quality)
  generated by the synthetic data pipeline, which models realistic degradation
  trajectories and injects ground-truth failure events for model training.
- **Weather forecasts** fetched from the Open-Meteo API for each asset's
  latitude/longitude — 48-hour and 7-day outlooks including temperature, wind speed,
  precipitation, and humidity.
- **Historical incident records** — past outage events keyed to asset and timestamp,
  used both as training labels and as a recency feature for risk scoring.

The key insight is that no single source is sufficient. Sensor readings alone miss
the weather context. Weather forecasts alone have no asset-level specificity.
Incident history alone is backward-looking. The fusion of all three is what makes
early, accurate risk detection possible.

### Step 2 — Feature Engineering

Raw sensor rows and weather records are transformed into a wide feature matrix — one
row per asset per scoring window. Computed features include:

- **Rolling statistics**: 24 h and 72 h rolling max and mean for each sensor dimension,
  capturing recent peak stress as well as sustained trend.
- **Rate-of-change features**: Δ per hour for temperature and vibration, which encode
  whether a sensor is accelerating toward a threshold or holding steady.
- **Baseline deviation (z-score)**: each reading normalised against the asset's own
  30-day historical baseline, separating genuinely anomalous readings from assets that
  simply run hot or vibrate more by design.
- **Weather context**: upcoming 48 h peak temperature and wind speed, joined from
  the weather forecast table by asset location.
- **Incident recency**: days since the most recent recorded failure on the same asset,
  which captures residual post-incident risk.

These features encode both *current state* and *trajectory*. An asset with a slightly
elevated temperature that is rising at 2 °C/h under an incoming heat dome is very
different from one with the same current reading that has been stable for three days.

### Step 3 — XGBoost Failure Probability Scoring

An XGBoost gradient-boosted classifier is trained on the engineered feature matrix
with a binary label: did this asset fail within the next 7 days? At inference time it
outputs a failure probability in [0, 1] for every asset in the current scoring window.

XGBoost was chosen over alternatives (logistic regression, neural networks) because:
- It handles mixed numeric feature types natively without normalisation
- It is robust to missing values, which are unavoidable in sensor data
- SHAP (SHapley Additive exPlanations) values integrate directly, providing
  per-prediction feature importance without additional modelling overhead
- Training on synthetic data of this size (tens of thousands of rows) completes in
  seconds, making rapid iteration practical

SHAP values are computed for every prediction. The top-contributing features for each
asset are passed downstream as part of the risk context, so the advisory layer can
reference them in its natural-language output.

### Step 4 — Severity Ranking

Failure probability alone is not the right dispatch criterion. A 70 % failure
probability on a remote, low-criticality switch serving 30 customers is less urgent
than a 40 % probability on a critical substation transformer serving 15,000 customers.

Grid Guard computes a composite severity score for each asset:

```
severity = failure_probability × log1p(customers_served) × criticality_tier
```

`log1p(customers_served)` compresses the customer count to prevent any single
large-feeder asset from arithmetically dominating every other. `criticality_tier`
is an integer (1–3) assigned during asset creation to reflect the asset's role in
grid topology (1 = standard distribution, 2 = key feeder, 3 = transmission or
substation backbone). The full fleet is sorted descending by severity and the
top-N assets are passed to the advisory step.

### Step 5 — IBM Bob / watsonx.ai Plan Generation

The top-ranked assets — along with their severity score, failure probability, top
SHAP-identified sensor features, and 48 h weather outlook — are serialised into a
structured prompt sent to IBM Bob via the watsonx.ai API.

The prompt is engineered to produce a concrete, prioritised maintenance plan rather
than a generic risk summary. Bob is explicitly instructed to:
- Name each asset and its location
- State the primary reason it was prioritised (sensor reading, weather context, or
  incident history, as identified by SHAP)
- Recommend a specific action: inspect, replace, pre-stage spares, or shed load
- Order recommendations by urgency

The result is a plain-English document that field supervisors can act on immediately
without interpreting model output or querying the database themselves.

## What Makes This Different from Naive Alternatives

**vs. threshold alerts alone:** Simple threshold alerts fire when a sensor crosses
a fixed value. They generate high volumes of false positives on assets that routinely
operate near thresholds, and they miss assets where the danger is in the *rate of
change* or the *combination* of moderately elevated readings across multiple sensors.
Grid Guard's ML layer learns multi-feature interaction patterns from historical
failure cases.

**vs. manual risk assessment:** An operator reviewing raw sensor dashboards for 50+
assets cannot mentally compute rolling statistics, z-scores, and weather context
simultaneously. Grid Guard automates the computation and presents only the ranked
result, reducing the cognitive load from "monitor everything" to "act on the top list."

**vs. a raw model output:** A failure probability number with no context requires
the operator to ask "why?" before they can dispatch. The SHAP-backed explanation and
IBM Bob plan generation answer that question before it is asked.

## User Experience

An operator's workflow with Grid Guard:

1. **Open the Streamlit dashboard.** The asset risk map loads, with markers coloured
   by severity score. Red markers indicate the highest-risk assets.

2. **Review the ranked risk table.** Each row shows: asset ID, asset type, location,
   failure probability, severity score, customers served, top sensor reading, and
   48 h weather outlook.

3. **Expand the maintenance plan panel.** The Bob-generated plan is displayed in
   plain English, naming each prioritised asset and recommending a specific action.

4. **Dispatch crews.** The plan is the dispatch brief. No additional interpretation
   is required.

## Key Design Decisions

| Decision | Rationale |
|---|---|
| **Neon Postgres as the central store** | A single relational database eliminates the integration complexity of separate time-series, feature, and model stores. Neon's serverless model makes it free between pipeline runs. |
| **Synthetic data for the demo** | Real utility SCADA data is proprietary and subject to strict access controls. Synthetic data with realistic degradation signatures and injected failure events is sufficient to demonstrate the full pipeline end-to-end. |
| **XGBoost over deep learning** | The feature matrix is tabular, the training dataset is modest in size, and SHAP explainability is a core requirement. XGBoost is the standard choice for this combination. |
| **IBM Bob as the advisory layer** | The advisory output must be readable and actionable by field supervisors who are not data scientists. Bob's natural-language generation converts structured risk data into the format operators actually use: a maintenance brief. |
| **FastAPI + Streamlit separation** | Keeping the API stateless and the frontend thin means the frontend can be replaced (e.g. with a React dashboard or a mobile app) without changing the scoring or advisory backend. |
